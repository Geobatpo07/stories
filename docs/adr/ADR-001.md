# ADR-001: MDX is the source of truth; DuckDB is a generated index

- **Status:** Accepted
- **Date:** 2026-07-24

## Context

Stories needs to store a growing, richly cross-referenced body of research content —
programs, questions, experiments, notes, software, publications, datasets — and needs to
query it efficiently (search, tag filters, "everything under this program," reverse
references) as the volume grows from dozens to potentially thousands of entries.

Two architectures were considered:

1. **Database as source of truth.** Content is entered into DuckDB (or another database)
   directly; MDX files, if any, are generated exports.
2. **Files as source of truth, database as generated index.** Content is authored as MDX
   files with YAML frontmatter, versioned in Git; a build step reads and validates every
   file and loads the result into DuckDB purely for fast querying.

## Decision

We chose option 2: **MDX is the single source of truth. DuckDB is only a generated
analytical index**, rebuildable at any time from `content/`.

## Why MDX is the source of truth

- **Git is the real audit trail.** A research notebook's core promise is that you can see
  how understanding evolved — including corrections and retractions. Git history on plain
  text files gives this for free: diffs, blame, and revert all work exactly as they do for
  code. A database row's history does not, without building that machinery separately.
- **Content review uses the same tools as code review.** A pull request that adds a
  Research Note reads like a pull request that adds a function — that's deliberate. It
  keeps the bar for "publishing" close to the bar for "shipping code," which fits a lab
  run by an engineer.
- **No lock-in, no migration risk.** Every entity is a portable text file. Changing the
  database engine, the framework, or the hosting provider later never risks the content
  itself — only the code that reads it.
- **Offline-legible.** A note is readable in any text editor, without the platform
  running at all. That matters for a notebook meant to outlive any one version of its own
  tooling.

## Why DuckDB, and only as an index

- **DuckDB is analytical, not transactional.** It is excellent at scanning and
  aggregating structured data (tag co-occurrence, cross-program timelines, full-text
  search) and is a single embedded file with no server to run — a good fit for a
  statically-generated Next.js site with no always-on backend.
- **It is explicitly disposable.** `database/generated/*.duckdb` is gitignored. Deleting
  it and running `pnpm db:index` must always be able to reproduce it from `content/`
  alone. If a fact only exists in DuckDB and not in a content file, that is a bug in the
  indexing step, not a feature.
- **It keeps `content/` boring.** Frontmatter stays simple, human-writable YAML. Anything
  that needs real querying (joins across entities, ranking, search) is pushed into the
  generated layer instead of turning frontmatter into a query language.

## Consequences

- Every content type needs a Zod schema (`domain/*/schema.ts`) that frontmatter is
  validated against at index-build time — a malformed file fails the build loudly instead
  of silently breaking a page later.
- Any feature that needs to *write* content programmatically (an editor UI, an API) must
  write MDX files, not database rows — the database is never the target of a write from
  application code, only from the indexing script.
- This constrains us against real-time collaborative editing of content (two people
  editing the same DuckDB row) — acceptable for a single-author research notebook today;
  revisit if the platform ever supports multiple simultaneous authors.
